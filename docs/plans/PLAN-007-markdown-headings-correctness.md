## Business requirements and constraints

Per [SPEC-005](../specifications/SPEC-005-markdown-headings-correctness.md) (approved) and [INIT-007](../initiatives/INIT-007-markdown-headings-correctness.md), this plan resolves the architectural "how" for a correctness pass on the shipped Markdown Headings commands — `tangyr.markdownHeadings.increment` and `tangyr.markdownHeadings.decrement` — with no change to their invocation surface. The corrected behavior is the specification's 28 acceptance criteria, referenced rather than restated here. The plan must:

- Compute fenced-code-block state over the **entire document** while confining the transform to the in-scope line set, so a heading's classification never depends on which fence lines a selection incidentally includes (SPEC-005 Code-block context integrity; AC1, AC2, AC3, AC4, AC10, AC23, AC26 — the SR-1/SR-2 core).
- Replace the all-or-nothing limit abort with a partial transform that moves every movable in-scope heading, leaves boundary headings in place, and reports a two-cause information-level no-op only when nothing moved (SPEC-005 Partial transform at level limits; AC5, AC6, AC7, AC8, AC10).
- Split notification levels: information for the no-op, warning or error for genuine invocation failures (SPEC-005 Error handling §1; AC9).
- Recognize ATX headings and fences by column-based indentation after tab expansion (0–3 columns), recognize bare ATX headings, preserve LF and CRLF endings exactly, and never treat a fence opener or closer as a heading (SPEC-005 ATX recognition, Bare ATX, Line-ending integrity, Fenced-code-block boundary correctness; AC11–AC22).
- Apply the corrected transform across every editor selection with a de-duplicated in-scope line set (SPEC-005 Multi-selection; AC24, AC25).
- Guarantee setext headings are never corrupted, by construction (SPEC-005 Setext heading handling; AC27, AC28).
- Ship the mixed ATX/setext desync known-limitation note on a user-facing surface in the same released version (SPEC-005 Known limitations; INIT-007 Scope).
- Deliver a test suite reflecting the corrected contract with no surviving test encoding the superseded behavior (SPEC-005 Behavioral delta and test impact; INIT-007 Scope), and pass the full quality gate (`check-types` + `lint` + `test:unit` + `test:integration:vitest`).

The feature is confined to one repository (`tangyr-vscode`) and one feature directory (`markdownHeadings`); no new command, configuration option, runtime dependency, or invocation surface is introduced.

## Alternatives considered

### Transform interface for full-document context (the SR-1/SR-2 core — SPEC-005 Code-block context integrity)

The root cause is that `command.ts` passes only the selected fragment's text to a transform that recomputes fence state from that fragment alone. The fix requires the transform to see the full document for classification while changing only in-scope lines. Three interface shapes were evaluated.

| Alternative  | Approach                                                                                                                                                                                                                                                                                                                           | Pros                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Cons                                                                                                                                                                                                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | The transform takes the full document text plus the set of in-scope line indices, computes code-block flags over the full text, transforms only in-scope ATX heading lines, and returns the full new document text plus an outcome describing what happened. The command replaces the whole document range with the returned text. | Classification is always full-document, so the selection's incidental inclusion or exclusion of a fence is structurally irrelevant (AC26 holds by construction); one code path serves both the selection and whole-document scopes and both the editor and Explorer entry points; lines outside the scope are returned byte-identical so confinement is guaranteed by the transform, not by the caller; the existing return-shape style (a discriminated result object) is preserved and extended | A whole-document range replacement is one undo unit and resets cursor/selection to the replaced range; the command must therefore inspect the outcome and perform no editor edit on a no-op (so an unchanged document yields no undo entry and no cursor move); undo granularity is coarser than a per-line edit                         |
| B            | The transform returns only per-line edits for the changed lines; the command applies a multi-edit that touches just those lines                                                                                                                                                                                                    | Finer undo granularity; cursor and unrelated selections perturbed minimally                                                                                                                                                                                                                                                                                                                                                                                                                       | The command must now own the mapping from changed-line indices back to document ranges and apply a batch edit — pushing transform mechanics into the command layer; multi-selection plus de-dup plus CRLF offset arithmetic in the command is materially more error-prone and harder to unit-test than a pure text-in/text-out transform |
| C            | Keep the fragment-only signature but have the command pre-scan the full document for the open/closed fence state at the scope's first line and pass that seed state into the fragment transform                                                                                                                                    | Smallest change to the existing signature                                                                                                                                                                                                                                                                                                                                                                                                                                                         | A seed boolean is insufficient: a fence opened above the scope and closed inside it, or a closer inside the scope whose opener is above, needs the full fence run length and character, not one boolean; reconstructing that in the command duplicates the fence scanner and reintroduces the exact class of boundary bug being fixed    |

Selection rationale: Alternative A makes the SR-1/SR-2 corruption structurally impossible — because classification always runs over the full document, no selection shape can change a heading's in-code/out-of-code status, which is precisely AC26's "selection result matches whole-document result per heading." It keeps the transform pure (full text and a line-index set in; full text and an outcome out), so every recognition and line-ending rule is exercised by fast unit tests without an editor. It preserves the project's established discriminated-result return style. The accepted cost — a single coarse undo unit and a cursor reset to the replaced range — is the conventional behavior of a document-rewriting editor command and is bounded by the byte-identical-outside-scope guarantee; the command suppresses the edit entirely on a no-op so an unchanged document is never replaced. Alternative B was rejected because it relocates transform mechanics (line-to-range mapping, multi-selection de-dup, CRLF offsets) into the command, fracturing testability and re-creating the boundary arithmetic that caused the original defect. Alternative C was rejected because a single seed boolean cannot carry the fence run length and character a straddling selection needs, so it would duplicate the fence scanner and reintroduce the boundary bug.

### Outcome shape carrying the partial-transform result (SPEC-005 Partial transform at level limits)

The transform must report whether anything changed and, when nothing changed, which of two causes applies, so the command can choose the notification level and message.

| Alternative  | Approach                                                                                                                                                                                                                                                                                                                              | Pros                                                                                                                                                                                                                                      | Cons                                                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | A single success-shaped result carrying the new text and an explicit outcome classification with three states: `changed` (at least one heading moved), `no-op: no transformable heading in scope`, and `no-op: all in-scope headings at the limit`. Genuine invocation failures are surfaced by the command layer, not by this result | One result type expresses every transform outcome; the two no-op causes are distinct enumerated values the command maps directly to its two messages (AC7, AC8); the boundary case is never an error, matching SPEC-005 Error handling §2 | The transform result no longer carries a failure variant, so the `error`-string contract the old tests asserted is removed — an intentional, breaking, observable change (handled in Increment 5 and called out per BK-006) |
| B            | Keep a boolean `changed` flag only; the command re-derives the no-op cause by re-scanning the scope                                                                                                                                                                                                                                   | Minimal result shape                                                                                                                                                                                                                      | The command would re-implement heading and limit detection to distinguish the two causes, duplicating transform logic and risking divergence between what the transform did and what the message claims                     |
| C            | Two-cause distinction implemented as two separate transform entry points the command calls in sequence                                                                                                                                                                                                                                | Each cause has its own function                                                                                                                                                                                                           | Splits one coherent pass into two; the document would be scanned twice and the "did anything move" answer could disagree between the two passes                                                                             |

Selection rationale: Alternative A keeps the transform the single authority on what happened — the command never re-derives heading state — and gives the command exactly the two enumerated no-op causes SPEC-005 requires it to distinguish. The discarded failure variant is the deliberate breaking change INIT-007 authorizes; the boundary condition becomes a no-op cause, never an error, satisfying SPEC-005 Error handling §2 by construction. Because a no-op is `changed: false`, the command keys its decision to write or edit on the `changed` state, not on a success flag (see Decision 3, and the no-op suppression points in Decision 1).

### Line-ending strategy (SPEC-005 Line-ending integrity)

The current path splits on `\n` and joins on `\n`, leaving a stray `\r` on every line of a CRLF document and skewing fence/heading recognition.

| Alternative  | Approach                                                                                                                                                                                                                                                                                                               | Pros                                                                                                                                                                                                                                                                               | Cons                                                                                                                                                                                                                        |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | Split the document into lines while capturing each line's own terminator, classify and transform on the terminator-free line content, then re-join each line with its original terminator preserved — so a mixed or uniform CRLF/LF document round-trips exactly and recognition runs on content with no `\r` artifact | Recognition is identical across LF and CRLF because it never sees a `\r` (AC15, AC16); CRLF closing-fence recognition works because the `\r` is a captured terminator, not trailing content (AC21, SPEC-005 fence §4); no ending is introduced, removed, or converted (AC15, AC16) | Requires the transform to track per-line terminators rather than a single split character — a deliberate structural change to the line model                                                                                |
| B            | Detect the dominant ending, normalize to LF for processing, then convert back to the dominant ending on output                                                                                                                                                                                                         | Simple internal model (LF only)                                                                                                                                                                                                                                                    | A document with mixed endings is silently homogenized — a content change SPEC-005 Constraint 2 forbids ("must not introduce, remove, or convert line endings"); the conversion is exactly the round-trip hazard being fixed |
| C            | Strip a trailing `\r` only inside the recognition predicates, leaving the join on `\n`                                                                                                                                                                                                                                 | Localized change to predicates                                                                                                                                                                                                                                                     | Recognition would be correct but output would still drop the `\r` on the join, converting CRLF to LF — fails AC16                                                                                                           |

Selection rationale: Alternative A is the only option that both recognizes identically across endings and preserves each line's ending byte-for-byte, including in the mixed-ending case SPEC-005 Constraint 2 protects. Normalization (B) and join-on-`\n` (C) each perform a conversion the specification forbids. The terminator-aware model also fixes the empty-document and no-trailing-newline round trips: an empty string carries no lines and no terminators, so it round-trips with no bytes added, and a final line without a terminator re-joins with no terminator appended (see Increment 1, BK-004).

The current `HEADING_RE`/`FENCE_RE` and the `trimStart`-based closing-fence check accept any leading indentation and measure spaces, not columns.

## Architectural decisions and rationale

### 1. Full-document context transform with whole-document replacement (the SR-1/SR-2 core — Alternative A)

Motivated by INIT-007 Objective 1 (safety: never corrupt non-heading content regardless of selection position) and SPEC-005 Code-block context integrity. The heading transform is reshaped to accept the full document text together with the set of in-scope line indices, to compute fenced-code-block flags across the entire document, to transform only those in-scope lines that are genuine ATX headings outside any code block, and to return the full new document text. Because classification always spans the whole document, a heading's in-code/out-of-code status is independent of which fence lines a selection happens to include — making AC26 ("selection result matches whole-document result per heading") true by construction and closing the SR-1 (selection inside a code block) and SR-2 (closing-fence-only selection) corruption paths. The command layer stops passing a context-free fragment: it supplies the whole document text and the in-scope line-index set, then replaces the whole-document range with the returned text. Lines outside the scope are returned byte-identical (SPEC-005 Code-block context integrity §3), so the whole-document replacement changes only in-scope headings.

**No-op performs no editor edit (normative).** The command inspects the transform's outcome state _before_ invoking any editor edit. On a `changed` outcome it performs the whole-document replacement. On either no-op outcome (no transformable heading in scope, or all in-scope headings at the limit) the command does **not** call `editor.edit()` at all: no undo entry is created, the cursor and selection are not moved, and the document is not marked modified. This is the normative behavior, not an optimization. (Defense-in-depth note: even were an edit issued, VS Code would coalesce a replacement whose value equals the current text; the command does not rely on that — it suppresses the edit by inspecting the outcome.) Trade-off accepted: when an edit _is_ performed, it is a single coarse undo unit and resets the cursor/selection to the replaced range — the conventional behavior of a document-rewriting command, bounded by the byte-identical-outside-scope guarantee. Risk cross-reference: Risks and mitigations, "coarse undo unit."

### 2. Partial transform at limits with a three-state outcome (Alternative A — outcome shape)

Motivated by INIT-007 Objective 2 (predictability) and SPEC-005 Partial transform at level limits. The whole-operation `validateHeadings` abort is removed. The transform moves every in-scope heading that can move in the requested direction and leaves boundary headings (level 6 under increment, level 1 under decrement) unchanged, never letting a boundary heading prevent other movements. The transform returns a single success-shaped outcome carrying the new text and a classification with three states: at least one heading moved; no transformable heading was in scope; or every in-scope heading was already at the limit. The boundary condition is one of the two no-op causes, never an error, satisfying SPEC-005 Error handling §2. This outcome is the command's sole authority on what happened — the command never re-scans to re-derive heading state, and it keys its decision to apply an editor edit or a file write on the `changed` state of this outcome (Decisions 1, 3, 4). Cross-reference: this removes the transform's failure variant, an intentional breaking change handled in Increment 5 and flagged per BK-006.

### 3. Notification level split with two distinct no-op messages (SPEC-005 Error handling §1; AC9)

Motivated by INIT-007 Objective 2 and SPEC-005 Partial transform at level limits §3–§4. The command layer maps the transform outcome to notifications: a `changed` outcome applies the edit and logs success with no user notification of failure; a "no transformable heading in scope" outcome shows a VS Code information-level notice with the corresponding cause message and performs no edit; an "all in-scope headings at the limit" outcome shows a VS Code information-level notice with the distinct boundary-cause message and performs no edit. The two no-op messages are textually distinct so the user can tell the causes apart (AC7, AC8). Genuine invocation failures — no active editor, or a non-Markdown Explorer target — retain their warning/error-level notices (AC9), and these guards are unchanged in behavior. The information-versus-warning/error split is the normative contract. This logic lives in the command layer because only it owns the VS Code notification surface; the transform stays pure.

### 4. Terminator-preserving line model for LF/CRLF integrity (Alternative A — line-ending strategy)

Motivated by SPEC-005 Line-ending integrity and Fenced-code-block boundary correctness §4. The transform models a document as a sequence of lines each carrying its own terminator (LF, CRLF, or none for a final unterminated line). Recognition and transformation operate on the terminator-free content, so a heading or fence recognized in an LF document is recognized identically in the byte-identical CRLF document (AC15, AC16), and a CRLF closing fence is recognized because the `\r` is a captured terminator rather than trailing content (AC21). On output each line is re-joined with its original terminator, so no ending is introduced, removed, or converted and no stray `\r` survives — including in a mixed-ending document, which is preserved rather than homogenized (SPEC-005 Constraint 2). The empty document carries no lines and round-trips with zero bytes added, and a final line without a terminator re-joins with no terminator appended, so a document lacking a trailing newline round-trips byte-identical (BK-004).

### 5. Column-based recognition predicates for ATX, bare ATX, and fences (Alternative A — recognition predicates)

Motivated by SPEC-005 ATX heading recognition, Bare ATX heading recognition, and Fenced-code-block boundary correctness, anchored to CommonMark (SPEC-005 Constraint 1). A shared column-measurement step computes leading indentation as columns after tab expansion (a tab advances to the next 4-column stop). ATX recognition admits a line whose first non-space content is a run of one to six `#` at 0–3 columns of indentation, where the run is terminated by a space, a tab, or the end of the line — the end-of-line terminator clause admitting a bare ATX heading with no title (AC14), and the 0–3 column bound rejecting a tab-indented `#` (which reaches column 4) as indented code (AC13). A `#` run immediately followed by a non-space, non-tab character (for example `#hashtag`) is not a heading (SPEC-005 ATX heading recognition §4). Fence recognition admits an opener whose fence run is at 0–3 columns; a closer must be at 0–3 columns, use the opener's character, be at least as long, and carry no non-whitespace trailing content (AC17–AC20). A fence line, opener or closer, is never evaluated as an ATX heading even when its content begins with `#` (AC20). When transformed, a heading's leading indentation and any trailing whitespace are preserved byte-for-byte and only the `#` run changes by one (SPEC-005 Constraint 2). Because the predicates are driven by column measurement rather than character counting, the over-indented-fence and tab-indented cases are handled correctly — superseding the current permissive matching.

**Classifier evaluation order (BK-003).** For each line, fence/code-block state is consulted **first**: the document is scanned top-to-bottom tracking open/closed fenced-code-block state, and a line that is a fence opener, a fence closer, or interior code is classified as in-block by that scan. Only a line that the fence scan leaves out of any code block is then offered to ATX recognition. ATX recognition therefore never runs on a fence line or an in-code line, which is what makes "a fence line is never evaluated as an ATX heading" (AC20) and "in-code `#` lines are inert" (AC1–AC4, AC10, AC22, AC23) hold by construction rather than by a later guard.

### 6. Multi-selection via a de-duplicated in-scope line-index set (SPEC-005 Multi-selection; AC24, AC25)

Motivated by INIT-007 Objective 1 and SPEC-005 Multi-selection. The command iterates every entry of the editor's selections, expands each to full lines (each partially-selected line counted in full), and unions their line indices into a single de-duplicated in-scope set before invoking the transform once. A line covered by two or more selections appears once in the set, so an overlapping selection shifts a heading by exactly one level (AC25); two disjoint selections each transform their headings (AC24); lines covered by no selection remain byte-identical because they are absent from the in-scope set and returned unchanged by Decision 1. When the editor has no selection, the in-scope set is every document line. This is the only place selection geometry is interpreted; the transform receives an abstract line-index set.

### 7. Setext non-corruption by construction (SPEC-005 Setext heading handling; AC27, AC28)

Motivated by SPEC-005 Setext heading handling and INIT-007's non-corruption guarantee for the untransformed heading form. No new logic targets setext structures: a setext underline (`=` or `-` run) does not begin with a `#` run, so it falls outside ATX recognition and is returned byte-identical (AC27); a setext text line likewise does not begin with `#` and is never transformed as an ATX heading (AC28). The guarantee is structural — it follows from ATX recognition requiring a leading `#` run — not from a setext detector, consistent with SPEC-005's decision that this iteration transforms ATX only and ships no in-product desync detector. The mixed-document desync this leaves is the documented known limitation (Decision 8).

### 8. Known-limitation note on the README and the CHANGELOG (Alternative A — note placement)

Motivated by INIT-007 Scope and SPEC-005 Known limitations §1. The README "Markdown Headings" section gains a "Known limitations" note stating that a document mixing ATX and setext headings has its ATX levels shifted while setext levels stay fixed, leaving the hierarchy internally inconsistent, and that no in-product detector is in scope. The same section's stale description of the old abort behavior is corrected to describe the partial transform and the information-level no-op, so the standing documentation matches the shipped behavior. The limitation is also recorded in the conventional-commit body that feeds the semantic-release CHANGELOG entry for the shipping version, satisfying INIT-007's dual named surface (README and CHANGELOG). The CHANGELOG route is already configured in `tangyr-vscode` (`.releaserc.json`), so no new release machinery is introduced; the note must ride the shipping release-triggering commit body (the breaking `fix`), because the project's release-notes preset hides and does not release `docs`-typed commits (Increment 7 confirms this).

## Increments

A single workstream on one shared branch is appropriate: every increment touches the same two source files (`headingTransform.ts`, `command.ts`) and their tests, so the increments are strictly sequential and concurrent execution would conflict on shared files. The internal order below is dependency-ordered; each increment is self-contained and introduces no forward reference. Each increment ends green on the full quality gate (`check-types` + `lint` + `test:unit` + `test:integration:vitest`).

### Increment 1 — Recognition core: column indentation, ATX/bare-ATX, fences, line-ending model

**Objective**: Establish the CommonMark-correct recognition substrate the rest of the plan builds on — column-based indentation after tab expansion, ATX and bare-ATX heading recognition, fence opener/closer recognition with 0–3 column bounds, and the terminator-preserving line model — without yet changing the command's scope handling.

**Dependencies**: none.

**Requirements covered**: SPEC-005 ATX heading recognition and indentation §1–§4; Bare ATX heading recognition §1; Line-ending integrity §1–§2; Fenced-code-block boundary correctness §1–§5; Constraint 1; Constraint 2; AC11, AC12, AC13, AC14, AC15, AC16, AC17, AC18, AC19, AC20, AC21, AC22.

**Interventions**:

- Introduce the shared column-measurement of leading indentation (tab advances to the next 4-column stop) used by both ATX and fence recognition (Decision 5).
- Replace the permissive ATX recognition so a heading is admitted only at 0–3 columns with the `#` run terminated by a space, a tab, or the end of the line — admitting bare ATX headings and rejecting tab-indented `#` and `#`-glued-to-text lines (Decision 5).
- Replace the permissive fence recognition so an opener is admitted only at 0–3 columns and a closer only at 0–3 columns with the opener's character, at least the opener's length, and no non-whitespace trailing content; ensure a fence line is never evaluated as an ATX heading, with fence/code-block state consulted before ATX recognition (Decision 5, BK-003).
- Introduce the terminator-preserving line model so recognition runs on terminator-free content and output re-joins each line with its original terminator, recognizing CRLF closing fences and preserving mixed and uniform endings exactly, with an empty document and a no-trailing-newline document both round-tripping byte-identical (Decision 4, BK-004).

**Verifiable output**: Unit tests prove indented ATX preservation (AC11), over-indented and tab-indented `#` left unchanged (AC12, AC13), bare ATX trailing-whitespace preservation under both directions (AC14), LF and CRLF round-trips with no `\r` artifact (AC15, AC16), over-indented and tab-indented fences not closing or opening a block (AC17, AC18, AC19), a fence info-string line beginning with `#` left unchanged (AC20), a CRLF closing fence recognized (AC21), and an unclosed fence protecting to end of document (AC22). A NEW over-indented-fence fixture is added — a fence line at 4 or more columns (four spaces, or a leading tab) — asserting that the over-indented fence line is treated as indented code, not a fence; this is an _added_ case, not an inversion. The existing 3-space (3-column) fence fixture around `headingTransform.test.ts:120-128` is VALID under both the old and new 0–3-column rules, so its assertion does not change and is not inverted (SPEC-005 Behavioral delta §2, C2). A round-trip test for the empty document and for a document with no trailing newline asserts byte-identical output with no bytes added (BK-004). The full quality gate passes.

### Increment 2 — Full-document context and confined transform (SR-1/SR-2 core)

**Objective**: Reshape the transform to classify code-block state over the entire document while confining changes to an in-scope line-index set, returning the full new document text — closing the SR-1/SR-2 corruption paths at the transform level.

**Dependencies**: Increment 1 (recognition substrate and line model).

**Requirements covered**: SPEC-005 Code-block context integrity §1–§3; Constraint 2 corollary (context independence); AC1, AC2, AC3, AC4, AC10, AC23, AC26.

**Interventions**:

- Change the transform interface to accept the full document text plus an in-scope line-index set, compute fence flags over the full text, transform only in-scope ATX heading lines outside any code block, and return the full new document text plus an outcome (Decision 1). The outcome's full classification shape is finalized in Increment 3; this increment delivers at least the "did anything change" signal needed to return correct text.
- Guarantee lines outside the in-scope set are returned byte-identical (Decision 1).

**Verifiable output**: Unit tests prove selected in-code content is inert under increment and decrement when the opener is above the scope (AC1, AC2), a closing-fence-only in-scope set (closer plus real heading, opener excluded) transforms only the real heading (AC3), a heading adjacent to a fence selected together with neighbouring fence lines transforms only the heading (AC4), a code-block-only in-scope set yields no change (AC10), a fully-interior selection inside an unclosed fence leaves selected `#` lines unchanged (AC23), out-of-scope lines are byte-identical (SPEC-005 Code-block context integrity §3), and a heading's per-line outcome is identical whether it is in a selection or the whole document (AC26). The full quality gate passes.

### Increment 4 — Command layer: full document, multi-selection de-dup, notification split

**Objective**: Make the command supply full-document text and a de-duplicated multi-selection in-scope set to the transform, replace the whole-document range with the result, suppress all editing/writing on a no-op outcome, and map the three-state outcome plus the unchanged failure guards to the correct notification levels.

**Dependencies**: Increments 2 and 3 (full-document transform and three-state outcome).

**Requirements covered**: SPEC-005 Code-block context integrity §3 (command confinement); Partial transform at level limits §3–§4; Multi-selection §1–§3; Error handling §1; Constraint 3; AC5, AC6 (command notification layer); AC7, AC8, AC9, AC24, AC25; SR-1/SR-2 fix at the command boundary.

**Interventions**:

- Stop passing a context-free fragment from `handleEditor`: supply the whole document text and the in-scope line-index set, then, on a `changed` outcome, replace the whole-document range with the returned text (Decision 1). Apply the same full-document path on the Explorer whole-file route (Decision 1, Decision 4 for CRLF on that path).
- Inspect the transform outcome _before_ any editing or writing. On either no-op cause the command performs no editor edit on the editor path — `editor.edit()` is not called, so no undo entry is created and the document is not marked modified (Decision 1, C3). On the Explorer path, call `fs.writeFile` only when the outcome is `changed`; on either no-op cause, show the information-level notice and return WITHOUT writing the file, since under the three-state outcome a no-op is `success: true` and the prior `if (!result.success) return` guard no longer suppresses the write (Decision 1, Decision 3, C4).
- Build the in-scope line-index set by iterating every editor selection, expanding each to full lines, and de-duplicating the union; use every line when there is no selection (Decision 6).
- Map the transform outcome to notifications: apply the edit on `changed` and report success with no warning (the command-side counterpart of AC5/AC6 — a movable heading shifts and the command reports success); show the information-level "no transformable heading in scope" notice or the distinct information-level "all in-scope headings at the limit" notice on the two no-op causes; retain the warning/error-level notices for no active editor and non-Markdown Explorer target (Decision 3).

**Verifiable output**: Command-layer unit tests prove the editor path passes full-document text (not a fragment) and replaces the whole-document range; on a `changed` outcome the command reports success and shows no warning (AC5/AC6, command notification layer); a no-op invocation on the editor path does NOT call `editor.edit()` and does not mark the document modified (C3); a no-op invocation on the Explorer path does NOT call `fs.writeFile` and shows the information-level notice (C4); two disjoint selections both transform and uncovered lines are byte-identical (AC24); overlapping selections shift a shared line exactly once (AC25); the two no-op causes surface at information level with distinct messages (AC7, AC8); and the no-active-editor and non-Markdown-target failures surface at warning/error level (AC9). The multi-selection-capable editor mock is added (a full-document `getText()` with no range argument plus a `selections` array). The full quality gate passes.

## Risks and mitigations

- Risk: The whole-document replacement (Decision 1) coarsens undo granularity and resets the cursor/selection to the replaced range.
  Mitigation: Accepted as conventional document-rewriting-command behavior; bounded by the byte-identical-outside-scope guarantee (SPEC-005 Code-block context integrity §3) so only in-scope headings change, and the command suppresses the editor edit and the file write entirely on a no-op outcome (it inspects the outcome before editing or writing), so an unchanged document is never replaced and a no-op leaves no undo entry.
- Risk: Removing the transform's `error`-string failure variant (Decision 2, BK-006) is an observable-output change that breaks any automation asserting those strings.
  Mitigation: Increment 5 runs a repository-wide search for both strings before the rewrite to account for every consumer (BK-005), calls the change out explicitly, and records it in the shipping commit body; the suite is rewritten to the new outcome so no internal consumer depends on the removed strings.
- Risk: The CRLF terminator-preserving model (Decision 4) is intricate and a regression could silently reintroduce a stray `\r` or convert endings.
  Mitigation: Increment 1 and Increment 5 add LF and CRLF round-trip tests on both the editor and Explorer paths (AC15, AC16, AC21, BK-007), and recognition runs on terminator-free content so a `\r` cannot skew matching.
- Risk: The multi-selection de-dup (Decision 6) could double-shift a line covered by overlapping selections.
  Mitigation: The in-scope set is a de-duplicated union of line indices, transformed once; AC25 is asserted directly in Increment 4.
- Risk: A no-op outcome being `success: true` (Decision 2) could let the command edit the editor or write the file when nothing changed, perturbing the cursor or touching the file's mtime.
  Mitigation: The command keys editing and writing on the `changed` state, not on success; Increment 4 asserts directly that a no-op invocation calls neither `editor.edit()` (C3) nor `fs.writeFile` (C4).
- Risk: The breaking behavior reaches users automatically via extension auto-update without an opt-in (INIT-007 Motivation).
  Mitigation: The recovery path is bounded — the prior Marketplace version remains installable via the version picker and a patch revert is the route back; the known-limitation note ships in the same version (Decision 8, Increment 7).
- Risk: A future contributor reintroduces fragment-only context handling in the command, re-opening SR-1/SR-2.
  Mitigation: The BK-005 representative integration test (Increment 5) and the per-heading selection-vs-whole-document equality test (AC26, Increment 2) fail if classification ever depends on selection shape.
