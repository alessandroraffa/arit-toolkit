## Business requirements and constraints

Per INIT-004, the plan must satisfy:

- In-editor editing of `SKILL.md` inside `.skill` ZIP archives via Explorer context menu and Command Palette.
- Automatic bundle repack on save, byte-preserving for all non-`SKILL.md` entries.
- Recovery flow when the bundle is moved, renamed, or deleted during editing.
- Template-based scaffolding when `SKILL.md` is absent from a bundle.
- Explicit error and abort on corrupted ZIP input.
- Concurrent-open behavior that focuses the existing tab instead of overwriting an in-progress buffer.
- Cleanup of extracted temp files on tab close and on activation sweep.

Extension-wide constraints inherited from the submodule architecture:

- Zero runtime dependencies. Any ZIP library enters the codebase as a dev dependency bundled by esbuild — the same model already used for `js-tiktoken` and `@anthropic-ai/tokenizer`.
- Feature isolation. The implementation lives under `src/features/skillBundleEdit/` with a single `registerSkillBundleEditFeature(ctx)` entry point. No imports from other features. Dependencies flow downward to `core/` and `utils/` only.
- ESLint complexity envelope for source files: 250 lines per file, 50 lines per function, cyclomatic complexity ≤ 10, max nesting 3, max parameters 3.
- TypeScript strict mode with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.
- Test-first development. Unit tests mock the VS Code API via `test/unit/mocks/vscode.ts`. New ZIP fixtures are added to `test/fixtures/` and consumed by both unit and integration tests.
- Disposable pattern. Every event subscription, command, watcher, and temp-file holder is registered on `context.subscriptions` for deterministic cleanup.
- Conventional Commits with lowercase subjects. Each increment lands as one or more atomic commits.

## Alternatives considered

### ZIP support library

| Alternative  | Approach                                                                                                | Pros                                                                                                                                                                                                                                                              | Cons                                                                                                                                                                                                                                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | `fflate` as a dev dependency bundled by esbuild                                                         | Small minified footprint relative to the existing bundle, zero transitive dependencies, MIT, actively maintained, synchronous API surface, supports reading and writing entries with explicit metadata control, matches the existing tokenizer-bundling precedent | One additional dev dependency to track. Requires verifying the bundle continues to externalize only the VS Code API.                                                                                                                                                                                                                                     |
| B            | Pure implementation against `node:zlib` (Local File Header, Central Directory, deflate, no third party) | Truly zero new dependencies                                                                                                                                                                                                                                       | Reimplements a well-understood format in product code. Substantial added surface (≥ 300 lines for read and write paths combined) that conflicts with the 250-line per-file ESLint limit, requires a sub-module split that does not reflect a domain decomposition, and pays an outsized maintenance cost for no incremental value over a vetted library. |

**Selection rationale.** Alternative A is consistent with the extension's existing strategy for capabilities the VS Code runtime does not provide directly: bundle the dependency at build time, keep runtime dependencies at zero. Re-implementing ZIP support would create a parser module larger than every other utility in `src/utils/` combined, for a problem space `fflate` solves with a stable, audited surface.

### Repack trigger

| Alternative  | Approach                                                                                    | Pros                                                                                                                    | Cons                                                                                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | Auto-repack on every save of the temp `SKILL.md` (`onDidSaveTextDocument` filtered by path) | Aligns with the user's mental model: save means persist. No additional UI surface. Each save is an atomic commit point. | Each save incurs ZIP I/O. A failed repack leaves the bundle untouched on disk; edit preservation is enforced by a `pendingFailure` flag on the session that keeps the temp file alive across tab close (Decisions 6, 10). |
| B            | Manual repack via explicit "Repack bundle" command                                          | Coarser control over when I/O happens                                                                                   | Decouples save from persistence — an anti-pattern in any editor workflow. The user has to remember the second action; forgetting it silently loses edits when the temp file is later cleaned up. Not viable.              |

**Selection rationale.** Alternative A maps directly to the editor convention that saving persists. The ZIP I/O cost is negligible for typical skill bundles (kilobytes to low single-digit megabytes). Failure paths are handled by tagging the session with a `pendingFailure` flag and preserving the temp file across tab close (Decisions 6, 10), so no edit is silently lost.

### Bundle integrity for non-edited entries

| Alternative                       | Approach                                                                                                                                                                                                                                                                                                                                                                                     | Pros                                                                                                                                                                                                                                                                                      | Cons                                                                                                                                                                                                                                                                                                                      |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected, WS-0017 disposition) | **Entry-splicing on raw archive bytes.** Parse the ZIP central directory to locate every entry. For each non-`SKILL.md` entry, retain its Local File Header + data block and its Central Directory record **verbatim**. Replace only the `SKILL.md` entry, recompute the central-directory offset of each retained entry by the size delta, and rebuild the End Of Central Directory record. | Companions keep their exact original bytes (compressed payload, CRC, version fields, flags, extra fields, comment). The only field that changes is the structural local-header-offset pointer, which is semantically required when an earlier entry resizes. Zero new runtime dependency. | Requires a small hand-written ZIP container reader/writer (central-directory parse, offset patch, EOCD rebuild — approx. 150–220 lines across helpers). More test surface than a library round-trip. A scoped form of the rejected "custom ZIP implementation" (ZIP-library Alternative B).                               |
| B (rejected at WS-0017 spike)     | Read entries and original metadata through `fflate`'s `Unzip` API; re-emit via `fflate.zipSync` with preserved metadata.                                                                                                                                                                                                                                                                     | Smaller code path; leans entirely on the bundled library.                                                                                                                                                                                                                                 | **Not achievable.** The WS-0017 Task 3.0 feasibility spike proved `fflate`'s `UnzipFile` surfaces only `name`/`compression`/`size`/`originalSize` (11 of the 13 required fields absent), and `zipSync` recompresses (no pre-compressed injection, no control over CRC/version/flag fields). Cannot deliver byte-identity. |
| C                                 | Decompress every entry, recompress all at write time, reset timestamps.                                                                                                                                                                                                                                                                                                                      | Simplest code path: one decompress-recompress cycle.                                                                                                                                                                                                                                      | Mutates metadata of files the user never touched; rewrites every binary asset with a potentially different compressed representation. Defeats the authoring-artifact preservation goal.                                                                                                                                   |

**Selection rationale.** Alternative A (entry-splicing) is the disposition recorded during WS-0017 execution after the Task 3.0 feasibility spike disproved the original `fflate`-round-trip approach (now Alternative B). Splicing reflects the principle that the tool modifies only what the user modifies: for a bundle containing binary assets, every non-edited entry's bytes are copied verbatim, guaranteeing diff cleanliness in any VCS tracking the `.skill` file. `fflate` remains bundled and is used only to decode the `SKILL.md` payload on read (`unzipSync`); the new `SKILL.md` entry is written as a stored (method 0) entry with a locally computed CRC-32, so the writer needs no library support. See Decision 2 for the resulting `CompanionEntry` model.

### Editing surface

| Alternative  | Approach                                                                                          | Pros                                                                                                                                                                            | Cons                                                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | Temp-file extraction plus the standard VS Code text editor, persisted via `onDidSaveTextDocument` | Zero new VS Code API surface; reuses every editor affordance (syntax highlighting, formatting, extensions, problem matchers); simplest first-iteration UX; lowest delivery risk | Editor tab label is the temp filename (`SKILL.md`) without bundle context; cross-bundle navigation requires re-invoking the command rather than browsing inside the archive                   |
| B            | `CustomTextEditorProvider` operating directly on the bundle URI with an internal virtual document | Tab label can carry the bundle identity; opens a future path toward editing other bundle entries; aligned with VS Code's first-class extension surface for non-text containers  | Substantial new VS Code API surface (provider lifecycle, virtual document synchronization, dirty-state propagation); duplicates editor affordances that the standard editor provides for free |

**Selection rationale.** Alternative A is chosen for v1 because it delivers the full INIT-004 success criteria without introducing new VS Code API surface. The `CustomTextEditorProvider` approach is documented as a v2 candidate in INIT-004's "Excluded" scope; the deferral is not re-litigated here.

## Architectural decisions and rationale

1. **Decision: feature module at `src/features/skillBundleEdit/` with a single registration entry point.**
   The feature follows the established Tangyr feature template: a directory under `src/features/<name>/` with an `index.ts` exporting `registerSkillBundleEditFeature(ctx)`. The feature depends only on `core/` (logger, command registry) and `utils/` (only if needed). No cross-feature imports. This addresses INIT-004 objective 1 by introducing the feature without coupling to existing features.
   _Trade-offs accepted:_ A new feature adds a registration call site in `extension.ts` and a new top-level entry under `src/features/`. This is the standard cost of adding any feature in the codebase.
   _Constraints:_ The feature registration must not introduce a new background service (no timers, no file watchers tied to lifecycle). The activation footprint is limited to command registration and a single startup sweep.

2. **Decision: `fflate` as a dev dependency, bundled by esbuild, with a `bundle.ts` entry-splicing adapter.**
   `fflate` enters as a dev dependency declared in `package.json` `devDependencies` (Increment 1) using the same caret-range convention already applied to `js-tiktoken` and `@anthropic-ai/tokenizer`. The exact resolved version is fixed by the lockfile; updates flow through the `dependency-governance` skill. `fflate` is bundled into `dist/extension.js` by esbuild, identically to how `js-tiktoken` and `@anthropic-ai/tokenizer` are bundled. `fflate`'s role is narrow: it decodes the `SKILL.md` payload on read (`unzipSync`). It is **not** used to round-trip companion entries — the WS-0017 Task 3.0 feasibility spike proved `fflate` cannot surface or reproduce the full ZIP metadata required for byte-identity (see Alternatives → "Bundle integrity", Alternative B). The `bundle.ts` adapter therefore implements **entry-splicing** over the raw archive bytes (Alternatives → "Bundle integrity", Alternative A) and exposes two domain operations: `readSkillBundle(uri): Promise<SkillBundleContent>` where `SkillBundleContent = { skillMd: string | undefined; companions: ReadonlyArray<CompanionEntry> }`, and `writeSkillBundle(uri, content): Promise<void>` taking the same `SkillBundleContent` shape — the adapter emits the archive with companion entries spliced in byte-for-byte. The public `SkillBundleContent` shape is stable; only the internal `CompanionEntry` shape reflects the splicing mechanism: `CompanionEntry = { name: string; localBlock: Uint8Array; centralHeader: Uint8Array }`, where `localBlock` is the verbatim Local File Header + file data and `centralHeader` is the verbatim Central Directory record (its 4-byte local-header-offset field is the only part patched at write time, when an earlier entry resizes). The adapter rejects encrypted entries (general-purpose bit 0 set) and ZIP64 entries (extra-field signature `0x0001`) with an unsupported-flag error consistent with Risk #1. This addresses INIT-004 objective 4.
   _Trade-offs accepted:_ One additional dev dependency in `package.json` (zero-transitive, well-maintained). A hand-written ZIP container reader/writer (central-directory parse, offset patch, EOCD rebuild, CRC-32 for the new `SKILL.md` entry) replaces the rejected library-round-trip path — more code and test surface, but the only path that delivers byte-identity (WS-0017 Task 3.0 disposition).
   _Constraints:_ The `bundle.ts` adapter must not import any VS Code API symbol. It receives URIs and returns plain data; the feature's command layer translates between the adapter and VS Code FS calls. The new `SKILL.md` entry is written as a stored (compression method 0) entry with a locally computed CRC-32.

3. **Decision: extracted `SKILL.md` lives at `extensionContext.globalStorageUri/skill-edits/<hash>/SKILL.md`.**
   The temp file path is derived from the SHA-1 hash of the bundle's absolute `fsPath`. This produces a stable, collision-resistant mapping from any bundle to one temp path. The hash also enables the activate sweep to identify orphan directories without needing a registry persisted across sessions. This addresses INIT-004 objective 3 (well-defined storage for the editing buffer).
   _Trade-offs accepted:_ The temp file path is opaque to the user. The editor tab will show "SKILL.md" as its label without contextual bundle name. Mitigation: a single information notification on open identifying the source bundle by name; further visual context is a v2 candidate.
   _Constraints:_ The hash uses only the absolute `fsPath` of the bundle. Bundles at different paths produce different hashes; the same bundle accessed via a symlink and via its canonical path (or via two case-variant paths on a case-insensitive filesystem) would produce different temp directories. This is consistent with VS Code's own handling of such paths and is documented in Risks; explicit detection is deferred to v2.

4. **Decision: in-memory `SessionRegistry` keyed by bundle `fsPath`, paired with an on-disk pending-failure sentinel.**
   A `Map<string, EditSession>` tracks the currently open edit sessions. Each `EditSession` holds the bundle URI, the temp file URI, the text document handle, the preserved companion entries from the original read (cached so the save path can repack without re-reading from disk and so the recovery path can include them in a new bundle even after the original is gone), and an optional `pendingFailure` state populated when a save-time repack fails (see Decision 6). The registry exposes `markFailure(bundleFsPath, failure)` and `clearFailure(bundleFsPath)` as the canonical API for mutating `pendingFailure`. As part of their contract, these two methods also write and remove a per-bundle on-disk sentinel file `.pending-failure.json` inside the bundle's `skill-edits/<hash>/` directory: `markFailure` writes the sentinel synchronously before returning (sentinel content is the serialized `PendingFailure` record — reason, message, timestamp — plus the bundle's absolute `fsPath` at the time of failure, retained for the recovery information notification), and `clearFailure` removes it. The in-memory `pendingFailure` field and the on-disk sentinel are kept in sync by these two methods exclusively; direct mutation of the `EditSession` object is not part of the contract, so failure state remains observable via a single seam for logging and testing. The registry is cleared on tab close subject to the conditional rule in Decision 10, and on extension deactivate. This addresses INIT-004 objective 3 (concurrent open behavior) and supports the recovery flow including cross-session preservation of pending-failure edits.
   _Trade-offs accepted:_ Memory holds the compressed bytes of companion entries for every open session. For typical skill bundles this is negligible (kilobytes per session); the registry caps in practice because the user opens a small handful at most. No persistent cache of session contents. The sentinel adds one small JSON file write on the failure path and one read per `skill-edits/<hash>/` subdirectory at activation time.
   _Constraints:_ The cached companion entries are the snapshot from open time, not the latest on-disk state. The v1 contract is single-author hands-off-while-editing: if the user externally modifies the bundle while a session is open, the next save overwrites those external modifications with the cached snapshot. External-modification conflict detection is deferred to v2 (see Risks).

5. **Decision: `SKILL.md` template scaffolding on missing-manifest bundles.**
   When a bundle is opened and `readSkillBundle` reports that no `SKILL.md` entry exists, the command prompts the user with two choices: create a new `SKILL.md` from the standard template, or abort. The template is a versioned constant in `template.ts` containing a valid YAML frontmatter (`name`, `description` fields) followed by markdown body comments that guide the author through the standard skill structure. The template does not include an H1 heading, in compliance with the project's authoring rule that documents with YAML frontmatter must not have a redundant H1. This addresses INIT-004 objective 3 (recovery from missing manifest).
   _Trade-offs accepted:_ The template is a single canonical structure. Authors with a different preferred skill layout will edit the template content away after the first save — acceptable, the template is a starting point, not a constraint.
   _Constraints:_ The template's frontmatter `name` field defaults to a placeholder derived from the bundle filename (lowercase, no extension). The user is expected to replace it before publishing the skill.

6. **Decision: auto-repack on `onDidSaveTextDocument` filtered by temp-file path, with explicit pending-failure state on error.**
   The feature subscribes to `vscode.workspace.onDidSaveTextDocument`. On each event, the handler checks whether the document's URI matches any session in the `SessionRegistry`. If matched, it reads the document text, calls `writeSkillBundle(session.bundleUri, { skillMd: newContent, companions: session.companions })`, and on success emits an info notification and clears `session.pendingFailure` via `clearFailure`. On failure, the handler calls `markFailure(session.bundleFsPath, { reason, message, timestamp })` before any notification is surfaced — the sentinel is durable from the moment the user becomes aware of the failure — and then surfaces a sticky error notification with action buttons "Retry" and (when the failure is `bundle-missing`) "Save as new bundle…". The call sequence is invariant: a `writeSkillBundle` rejection causes `markFailure` to be invoked synchronously in the rejection handler before any UI call, so no window exists between document-clean state and durable failure state. The "Retry" button re-invokes `writeSkillBundle(session.bundleUri, { skillMd: currentBufferContent, companions: session.companions })` directly, bypassing the `onDidSaveTextDocument` event loop because the save event has already fired and the document is already clean from VS Code's perspective. Edit preservation under failure does not rely on dirty-buffer semantics — `onDidSaveTextDocument` fires after VS Code has already marked the document clean, and there is no first-class API to revert that. Edit preservation is instead enforced by the conditional tab-close cleanup in Decision 10, which preserves the temp file as long as the session has a pending failure. This addresses INIT-004 objective 2 (automatic repack).
   _Trade-offs accepted:_ A save triggers a full bundle rewrite even if the user pressed save with no changes. The cost is negligible for typical sizes. The user cannot rely on VS Code's native dirty-state indicator to signal a pending repack failure — the sticky notification and the tab-close-time information notification (Decision 10) are the only signals until the user retries or invokes Save As.
   _Constraints:_ The handler must filter events by path containing the `skill-edits/` segment to avoid running on unrelated document saves elsewhere in the workspace. The pending-failure record uses a discriminated union over `reason` (`bundle-missing`, `repack-io-error`, `rename-failed`, etc.) so the notification surface can present reason-appropriate actions.

7. **Decision: bundle-moved-or-deleted detection with "Save as new bundle" recovery.**
   Before each repack, the handler calls `vscode.workspace.fs.stat` on the bundle URI. If `stat` throws `FileNotFound`, the handler marks the session with `pendingFailure = { reason: 'bundle-missing', … }` per Decision 6 and surfaces a sticky error notification with the two action buttons established in Decision 6: "Retry" (re-invokes the repack against the same `session.bundleUri`, useful when the bundle reappears at the original path) and "Save as new bundle…". Clicking "Save as new bundle…" opens `vscode.window.showSaveDialog` filtered to `.skill` extension. On confirmation, the handler calls `writeSkillBundle(chosenUri, { skillMd: currentBufferContent, companions: session.companions })`, rebinds `session.bundleUri` to the new path, and clears `session.pendingFailure`. On dialog cancel, `session.pendingFailure` is preserved so the conditional cleanup in Decision 10 protects the temp file from deletion until the user resolves the failure. This addresses INIT-004 objective 3 (recovery from bundle move/delete).
   _Trade-offs accepted:_ The recovery dialog is one extra interaction step. Cancelling the dialog leaves the session in a "pending failure" state — the user must retry the dialog, invoke "Save as new bundle…" again from the sticky notification, or close the tab (which under Decision 10 will preserve the temp file and surface the path so the content can be recovered manually).
   _Constraints:_ The recovery path uses only the cached companion entries from the open-time snapshot. If the user wanted to incorporate file changes that occurred between open and recovery, they would need to close the buffer and reopen the new bundle.

8. **Decision: corrupted ZIP detection at open time, hard abort.**
   When `readSkillBundle` throws — invalid signature, truncated central directory, any other malformed input — the open command surfaces an error notification with the parser's message, logs the failure via the singleton `Logger`, and aborts. No temp file is created and no editor tab is opened. This addresses INIT-004 objective 3 (graceful handling of malformed input).
   _Trade-offs accepted:_ The user cannot "force open" a corrupted bundle through the feature. Repairing a corrupted ZIP is out of scope and not what the feature is for.
   _Constraints:_ The error message identifies the bundle by basename and includes the parser's exception message for diagnostic value.

9. **Decision: concurrent open focuses the existing editor tab.**
   When the edit command is invoked on a bundle whose `fsPath` already has an entry in `SessionRegistry`, the handler calls `vscode.window.showTextDocument(existingSession.document)` to focus the existing tab and returns without re-extracting. This addresses INIT-004 objective 3 (concurrent open behavior).
   _Trade-offs accepted:_ If the existing session was somehow corrupted (the user manually deleted the temp file while the tab was open), the focus action will succeed but subsequent saves may fail. The activate sweep mitigates the cross-session case; in-session manual deletion of the temp file is outside the feature's protection envelope.
   _Constraints:_ The registry lookup uses the canonical `fsPath` of the bundle URI; symlink and case-normalization edge cases follow VS Code's own handling (see Risks).

10. **Decision: sentinel-aware cleanup on tab close plus sentinel-aware activate sweep.**
    Two cleanup mechanisms operate in tandem. (a) `onDidCloseTextDocument` consults the session's `pendingFailure` state: when `undefined`, the handler deletes the temp file and removes the entry from the registry; when a pending failure exists, the temp file and the on-disk `.pending-failure.json` sentinel (already written by `markFailure` per Decision 4) are preserved, the registry entry is preserved, and an information notification is shown identifying the bundle, the failure reason, and the absolute path of the preserved temp file so the user can recover the content manually. (b) On `registerSkillBundleEditFeature(ctx)` invocation at extension activation, the feature performs a sentinel-aware sweep: it reads each direct child of `globalStorageUri/skill-edits/`, removes every subdirectory that does not contain a `.pending-failure.json` sentinel, and preserves every subdirectory that does. The paths and serialized failure metadata of preserved subdirectories are surfaced to the user via an information notification at activation time, one per preserved record, identifying the bundle, the failure reason, and the absolute filesystem path of the preserved temp file. This addresses INIT-004 objective 3 (deterministic temp-file lifecycle with edit preservation under failure that survives crash, OS kill, and VS Code restart).
    _Trade-offs accepted:_ The activation path performs one extra read per `skill-edits/<hash>/` subdirectory to check for the sentinel. The activation notification surface may emit multiple notifications when several unresolved failures accumulated across crashes; in practice this number is small because the user opens a small handful of bundles at a time.
    _Constraints:_ The activate sweep must run before any command can be invoked. It is sequenced ahead of feature registration: the sweep promise resolves before the first command handler is exposed. The information notifications on activation and on close-with-pending-failure must include the absolute filesystem path of the temp file (not the VS Code URI) so the user can open it in another editor or copy it with a shell command.

## Increments

### Increment 1 — Bundle I/O foundation and template

**Objective.** A pure, VS-Code-free adapter that reads and writes `.skill` ZIP archives with byte-preserving handling of non-`SKILL.md` entries. The standard `SKILL.md` template is encoded as a constant available for downstream increments.

**Dependencies.** None.

**Requirements covered.** INIT-004 objectives 2 (byte-preserving repack) and 4 (zero runtime dependency posture).

**Interventions.**

- Add `fflate` to `package.json` `devDependencies` with a caret-range version specifier consistent with the existing `js-tiktoken` and `@anthropic-ai/tokenizer` entries (lockfile pins the exact resolved version). Verify esbuild bundles it into `dist/extension.js`. Add an integration check that the production bundle does not externalize `fflate`. The bundling check searches the bundle text for two `fflate` top-level export symbols that must be present after inlining — `unzipSync` and `zipSync` — and asserts the absence of `require("fflate")`, mirroring the existing tokenizer pattern (`getEncoding`, `Tiktoken` presence; absence of `tiktoken_bg.wasm`).
- Create `src/features/skillBundleEdit/bundle.ts` exposing `readSkillBundle(uri): Promise<SkillBundleContent>` and `writeSkillBundle(uri, content): Promise<void>`. `SkillBundleContent` is `{ skillMd: string | undefined; companions: ReadonlyArray<CompanionEntry> }` where `CompanionEntry` carries the full set of fields required for byte-preserving rewrite of the original central-directory record: name, compressed bytes, compression method, CRC, mtime, version-made-by, version-needed-to-extract, general-purpose bit flag, internal attributes, external attributes, file comment, Local File Header extra fields, and Central Directory extra fields. The implementation rejects malformed input by throwing a typed `SkillBundleError` and rejects any entry whose general-purpose bit flag declares encryption or whose record uses ZIP64 extensions with an unsupported-flag error (consistent with Risk #1). Path validation rejects entry names containing `..`, absolute prefixes, and null bytes so malformed names cannot be propagated into the rewritten archive's central directory.
- Create `src/features/skillBundleEdit/template.ts` exposing `SKILL_MD_TEMPLATE: string` containing valid YAML frontmatter with `name` and `description` placeholder fields followed by markdown body comments that scaffold the standard skill structure. The template starts with the frontmatter delimiter (no H1).
- In `src/features/skillBundleEdit/index.ts`, declare the command ID (`tangyr.editSkillBundle`), the `skill-edits` directory name, and the temp-file basename (`SKILL.md`) as top-level `const` exports. These identifier constants are co-located with the feature registration entry — their primary consumer — and are imported by `command.ts` (command ID lookup) and `tempStore.ts` (directory name and basename). Avoids a one-import-only `constants.ts` module while keeping content (`template.ts`) and identifiers (`index.ts`) in semantically separated homes.
- Create test fixtures under `test/fixtures/skill-bundles/`: `valid-with-skill-md.skill`, `valid-no-skill-md.skill`, `valid-empty-skill-md.skill`, `valid-with-companions.skill` (multiple entries), and `invalid-not-zip.skill`. Fixtures are generated by a setup helper that uses `fflate` directly to ensure determinism.
- Write unit tests in `test/unit/features/skillBundleEdit/bundle.test.ts` covering: round-trip read-write of every fixture, byte-identical preservation of companion entries verified by SHA-256 of the central-directory bytes for each preserved entry (not only the compressed payload), replacement of `SKILL.md` content without affecting companions, rejection of malformed input with typed error, rejection of entry names containing `..`, absolute prefixes, or null bytes, and rejection of unsupported flags (encryption, ZIP64).
- Write unit tests for the template constant covering: parseable YAML frontmatter, presence of the required `name` and `description` keys, absence of an H1 heading after the frontmatter delimiter.

**Verifiable output.** Unit tests pass. The integration check confirms that `pnpm run compile` produces a `dist/extension.js` containing the `unzipSync` and `zipSync` tokens from `fflate` and not containing `require("fflate")`. The `bundle.ts` adapter has no VS Code import, verified by a static check in the test suite.

### Increment 2 — Edit session: open, concurrent open, missing-manifest, corrupted-input

**Objective.** A working "open SKILL.md from bundle" workflow: invoking the command on a `.skill` extracts the manifest into a temp file under `globalStorageUri/skill-edits/<hash>/SKILL.md` and opens it in a standard editor tab. Concurrent invocations focus the existing tab. Missing-manifest cases offer the template. Corrupted input aborts cleanly.

**Dependencies.** Increment 1.

**Requirements covered.** INIT-004 objectives 1 (in-editor editing), 3 (concurrent open, missing manifest, corrupted input).

**Interventions.**

- Create `src/features/skillBundleEdit/tempStore.ts` exposing `resolveTempUri(bundleUri): vscode.Uri` (SHA-1 of `fsPath` → `globalStorageUri/skill-edits/<hash>/SKILL.md`), `writeTempFile(uri, content): Promise<void>`, `deleteTempDir(uri): Promise<void>`, and `sweepOrphans(): Promise<ReadonlyArray<PreservedFailureRecord>>`. `sweepOrphans()` reads each direct child of `globalStorageUri/skill-edits/`; for each subdirectory it checks for the presence of `.pending-failure.json`; subdirectories containing the sentinel are preserved and a `PreservedFailureRecord` is appended to the return value (carrying the bundle `fsPath`, the failure `reason`, the failure `message`, the failure `timestamp`, and the absolute filesystem path of the preserved temp file); subdirectories without the sentinel are removed. `PreservedFailureRecord` is exported from this module so the activation path can consume it.
- Create `src/features/skillBundleEdit/session.ts` exposing a `SessionRegistry` class with `get(bundleFsPath): EditSession | undefined`, `set(session)`, `delete(bundleFsPath)`, `markFailure(bundleFsPath, failure: PendingFailure)`, `clearFailure(bundleFsPath)`, and `entries()`. `EditSession` is `{ bundleUri: vscode.Uri; tempUri: vscode.Uri; document: vscode.TextDocument; companions: ReadonlyArray<CompanionEntry>; pendingFailure?: PendingFailure }`. `PendingFailure` is a discriminated union over `reason: 'bundle-missing' | 'repack-io-error' | 'rename-failed'` with `message: string` and `timestamp: number`. As part of the contract established in Decision 4, `markFailure` writes the on-disk `.pending-failure.json` sentinel inside the bundle's `skill-edits/<hash>/` directory synchronously before returning (sentinel content is the serialized `PendingFailure` plus the bundle's absolute `fsPath`), and `clearFailure` removes the sentinel. In-memory state and the on-disk sentinel are kept in sync exclusively via these two methods.
- Create `src/features/skillBundleEdit/command.ts` exposing `editSkillBundleCommand(bundleUri, ctx, registry)` that: (a) checks the registry for an existing session and reveals its document if present; (b) otherwise calls `readSkillBundle` and handles the four cases — `SKILL.md` present (extract and open), `SKILL.md` absent (prompt user; on accept, scaffold from template; on decline, abort), corrupted (error notification + log + abort), I/O error (error notification + log + abort); (c) on extract or scaffold success, writes the temp file, opens the document, registers the session, and emits a single info notification identifying the source bundle by basename.
- Create `src/features/skillBundleEdit/index.ts` exposing `registerSkillBundleEditFeature(ctx)` that: (a) awaits `sweepOrphans()`; (b) when the returned `ReadonlyArray<PreservedFailureRecord>` is non-empty, emits one information notification per preserved record identifying the bundle, the failure reason, and the absolute filesystem path of the preserved temp file; (c) registers `tangyr.editSkillBundle` via the `CommandRegistry`; (d) returns a `Disposable` aggregating the command and the registry cleanup.
- Wire the feature into `src/extension.ts` after the existing feature registrations.
- Update `package.json` `contributes`: add the `tangyr.editSkillBundle` command, add an `explorer/context` menu entry conditioned on `resourceExtname == .skill`, and add a command-palette entry conditioned on the workspace being single-root (consistent with the existing pattern for stateful features).
- Unit tests in `test/unit/features/skillBundleEdit/`: `tempStore.test.ts` (hash determinism, sweep idempotence, write/delete round trip, sentinel-aware sweep preserves subdirectories containing `.pending-failure.json` and removes those without, returned `PreservedFailureRecord` entries carry the expected fields), `session.test.ts` (registry behavior, `markFailure` writes the sentinel file with expected JSON content, `clearFailure` removes the sentinel file, in-memory and on-disk state stay in sync across calls), `command.test.ts` (every branch — fresh open, concurrent open focus, missing-manifest accept and decline, corrupted abort).

**Verifiable output.** Unit tests pass. A manual VS Code Extension Host smoke test confirms that right-clicking a fixture `.skill` shows the new context-menu item, that opening a valid bundle reveals the `SKILL.md` content in a standard editor tab, that re-invoking on the same bundle focuses the existing tab, that opening a bundle without `SKILL.md` prompts and (on accept) opens the template, and that opening a corrupted bundle shows an error and creates no tab.

### Increment 3 — Save flow, recovery flow, and cleanup lifecycle

**Objective.** The full edit-and-persist cycle: saving the open `SKILL.md` repacks the bundle byte-preservingly. Bundle moved or deleted at save time produces a recovery flow that creates a new `.skill`. Temp files are cleaned up on tab close and on activation sweep. Unresolved pending failures are preserved across crash, OS kill, and VS Code restart via the on-disk sentinel.

**Dependencies.** Increment 1, Increment 2.

**Requirements covered.** INIT-004 objectives 2 (auto-repack on save) and 3 (recovery from bundle move/delete, cleanup lifecycle).

**Interventions.**

- Extend `src/features/skillBundleEdit/command.ts` (or add a sibling `saveHandler.ts` if the command file approaches the 250-line limit) with a save listener registered on `vscode.workspace.onDidSaveTextDocument`. The listener filters by document URI matching a path under `globalStorageUri/skill-edits/`, looks up the session, performs a `stat` on the bundle URI, and either repacks (success path — `clearFailure` is called, which clears the in-memory `pendingFailure` and removes the on-disk `.pending-failure.json` sentinel) or invokes `markFailure` (failure path — `markFailure` writes the on-disk sentinel synchronously before the notification is surfaced, so the failure record is durable from the moment the user sees it; the call sequence in the rejection handler is `markFailure` first, notification afterward).
- Implement the recovery flow: a sticky error notification with action buttons "Retry" and (when `reason === 'bundle-missing'`) "Save as new bundle…". The "Retry" handler re-invokes `writeSkillBundle(session.bundleUri, { skillMd: currentBufferContent, companions: session.companions })` directly — it bypasses the `onDidSaveTextDocument` event loop because the document is already clean from VS Code's perspective and triggering another save would not produce a new event. On "Save as new bundle…" click, `vscode.window.showSaveDialog` with `.skill` filter; on confirm, `writeSkillBundle(chosenUri, { skillMd: currentBufferContent, companions: session.companions })` produces the new bundle, the session's `bundleUri` is rebound, and `clearFailure` removes both the in-memory `pendingFailure` and the on-disk sentinel. On dialog cancel, `pendingFailure` (and its on-disk sentinel) are preserved so the conditional tab-close cleanup keeps the temp file alive.
- Implement repack atomicity with an explicit failure invariant: the original bundle file is preserved across any rename-path failure. Write the new content to `<bundle>.skill.tmp-<pid>-<nonce>` in the same directory as the bundle. Issue `vscode.workspace.fs.rename(tempPath, bundleUri, { overwrite: true })`. On success, no further action. On failure, delete the temp file, call `markFailure({ reason: 'rename-failed', message, timestamp })` (which also writes the on-disk sentinel), surface an error notification with the "Retry" action, and leave the original bundle untouched. Document the known v1 limitations: on Windows, rename-over-existing may fail when the bundle file is locked by another process; on non-POSIX network mounts (SMB, NFS without atomic rename support), the rename is not guaranteed atomic — in both cases the failure is surfaced through the standard `pendingFailure` flow, edits are preserved, and the original bundle is not modified.
- Implement sentinel-aware tab-close cleanup: subscribe to `vscode.workspace.onDidCloseTextDocument`, look up the session by document URI, and branch on `session.pendingFailure`. When undefined, call `deleteTempDir(session.tempUri.parent)` and remove the entry from the registry. When defined, leave the temp file and the on-disk `.pending-failure.json` sentinel in place (no extra action is required because the sentinel was already written by `markFailure`; the close handler simply skips `deleteTempDir`), keep the registry entry, and show an information notification including the bundle basename, the failure reason, and the absolute filesystem path of the preserved temp file.
- Register both new event listeners (`onDidSaveTextDocument` and `onDidCloseTextDocument`) on `context.subscriptions` via the aggregating `Disposable` returned by `registerSkillBundleEditFeature`, in accordance with the Disposable pattern stated in the business requirements.
- Verify that the sentinel-aware activate sweep added in Increment 2 correctly removes sentinel-free orphans and preserves sentinel-bearing subdirectories from prior sessions, including pending-failure temp files from crash/OS-kill/reload (integration test).
- Unit tests covering: save success calls `clearFailure` (in-memory cleared, sentinel file removed) and writes byte-equal expected bundle; save failure with bundle missing sets `pendingFailure.reason = 'bundle-missing'`, writes the sentinel file with expected JSON content, and invokes the recovery dialog; recovery confirm writes a new bundle, rebinds the session, and clears both in-memory and on-disk failure state; recovery cancel keeps `pendingFailure` set and sentinel on disk; save failure with disk I/O error sets `pendingFailure.reason = 'repack-io-error'` and writes the sentinel; rename-failed path: when `vscode.workspace.fs.rename` is mocked to throw, the temp file is removed, `pendingFailure.reason` is `'rename-failed'`, the error notification is surfaced, and a follow-up `stat` on the original bundle URI confirms it is untouched (size and mtime unchanged from pre-save state); tab close with `pendingFailure === undefined` removes the temp dir and registry entry; tab close with `pendingFailure` set preserves both the temp file and the sentinel and emits the recovery notification with the temp-file path; `sweepOrphans` preserves directories containing `.pending-failure.json` and returns the corresponding `PreservedFailureRecord` entries; activation surfaces one information notification per preserved record.
- Integration tests as flat files under `test/integration/vitest/`: `skill-bundle-roundtrip.test.ts` exercises the bundled `dist/extension.js` with read-modify-write on a real `.skill` fixture and verifies byte-identical companions via SHA-256 of the central-directory entries; `skill-bundle-bundling.test.ts` asserts that `fflate` symbols (`unzipSync`, `zipSync`) are inlined into the production `dist/extension.js` and that `require("fflate")` is absent.

**Verifiable output.** Unit and integration tests pass. A manual smoke test confirms that saving the open `SKILL.md` updates the `.skill` file on disk (verified by extracting the resulting archive and comparing companion checksums), that deleting the bundle before save and then saving shows the recovery dialog and produces a valid new bundle at the chosen location, and that closing the tab removes the temp directory. An integration test simulates a rename failure (e.g., by holding a file lock or pointing the bundle URI at a directory) and verifies the original bundle bytes are unchanged after the failure path completes.

## Risks and mitigations

- **Risk: `fflate` semantics differ from the canonical ZIP specification in some edge case (e.g., non-standard compression method, ZIP64 sizes).**
  **Mitigation:** The `bundle.ts` adapter normalizes through `fflate`'s explicit API and the integration tests cover representative fixture shapes. Bundles that use uncommon features (encryption, ZIP64) are explicitly out of scope for v1; the adapter throws on unsupported flags with a clear error message.

- **Risk: race condition between the open-time companion-entry snapshot and an external modification of the bundle while the buffer is open.**
  **Mitigation:** The save handler performs a `stat` check before writing. A change in size or mtime since open could be surfaced as a conflict notification — deferred to v2 as the feature's contract is single-author editing. In v1, the external modification is overwritten with the snapshot view on save.

- **Risk: activation overhead from the orphan sweep on large `skill-edits/` directories accumulated from crashes.**
  **Mitigation:** The sweep is a single `readDirectory` followed by a per-subdirectory sentinel check and recursive deletes for sentinel-free entries. The directory rarely accumulates more than a handful of subdirectories because the in-session cleanup is reliable. If observability shows otherwise, the sweep can be moved to an idle callback (`setTimeout` post-activation) without changing semantics.

- **Risk: package-size regression from bundling `fflate` into `dist/extension.js`.**
  **Mitigation:** `fflate` is small relative to the current `dist/extension.js`, which is dominated by tokenizer vocabularies. The added size is well under one percent of the existing bundle and well below typical VS Code Marketplace acceptance thresholds.

- **Risk: the `SKILL.md` template ages out of alignment with the evolving skill protocol.**
  **Mitigation:** The template is a single constant in `template.ts`, easy to update. The template is documented as a starting point, not a contract, and is exercised by tests for shape (valid frontmatter, no H1) rather than for exact content.

- **Risk: pending-failure state lost on extension reload or VS Code restart.**
  **Mitigation:** Pending-failure state survives extension reload and VS Code restart via the per-failure on-disk `.pending-failure.json` sentinel written by `markFailure` inside each bundle's `skill-edits/<hash>/` directory (Decision 4). The sentinel-aware activate sweep (Decision 10) reads each `skill-edits/<hash>/` subdirectory: subdirectories with the sentinel are preserved and surfaced to the user via an activation-time information notification identifying the bundle, the failure reason, and the absolute filesystem path of the preserved temp file; subdirectories without the sentinel are removed. The user is therefore aware on any cold start with preserved edits, and edits remain recoverable from disk until the user resolves the failure (retry, save-as-new-bundle, or manual copy).

- **Risk: identity ambiguity for bundles accessed via symlink or via case-variant paths on case-insensitive filesystems.**
  **Mitigation:** The session identity is the canonical `fsPath` of the bundle URI (Decisions 3, 9). Opening the same underlying file via a symlink and via its canonical path — or via two case-variant paths on a case-insensitive filesystem — produces two distinct `fsPath` strings, two distinct session entries in the registry, and two distinct temp directories. This mirrors VS Code's own behavior for any file opened via two distinct paths. Explicit canonicalization (e.g., `realpath` resolution or case-folded comparison) is deferred to v2; in v1 the user can avoid the ambiguity by always opening the bundle through the same path.
