## Business requirements and constraints

Per [SPEC-004](../specifications/SPEC-004-assistant-popularity-ranking.md) (approved) and [INIT-006](../initiatives/INIT-006-assistant-popularity-ranking.md), the plan must deliver a single governing popularity order over the eight supported targets — Claude Code, Cline, GitHub Copilot Chat, OpenAI Codex, OpenCode, Aider, RooCode, Continue — that: derives from exactly one versioned artifact consumed identically by the README and the runtime; is a stable total order produced by per-signal dense ranking, pool-size-comparable normalization, average-of-normalized-positions scoring over possessed signals, ascending, with a case-insensitive ASCII alphabetical canonical-name tie-break; tolerates missing surfaces (an absent or contract-failing signal simply does not participate, never zero, never error); records per-target provenance (raw signals, source, period) so each score is recomputable; is refreshed monthly by a build-time step that queries public sources and proposes its change through a pull request under the existing human merge authorization; introduces zero new runtime dependency and performs no network call at runtime; and leaves archiving correctness unchanged, proven by a provider-registry order-sensitivity audit plus a swap-invariance regression test. Every public surface of the order — the README and the published data artifact alike — carries a not-an-endorsement disclaimer, a pointer to the documented method, and an "as of `<last refresh>`" marker.

This plan resolves the four items SPEC-004 deferred to the plan gate: the **mechanism-feasibility gate** (per-target, per-surface source confirmation with concrete identifiers — Data-source feasibility status, below), the **exact normalization arithmetic** (Architectural decision 1), the **per-source validity contract**, **build-time credential handling**, and the **maintenance owner plus acceptable-staleness window** (Architectural decisions 3 and 7). **The mechanism-feasibility gate is cleared: every target resolves to at least one verified public signal, and no surface required guessing — absent surfaces are recorded as absent under the missing-surface tolerance, never invented.**

This optional read-only popularity-data credential is distinct from, and far narrower than, the `GITHUB_TOKEN` write-scope credential the workflow uses to open the refresh pull request (Architectural decision 3, Credential handling).

## Alternatives considered

### Normalization arithmetic (SPEC-004 Aggregation model §4, the deferred mechanism)

SPEC-004 fixes the _property_: per-signal dense rank, normalized to a pool-size-comparable position with the best end (most popular) denoting the top standing, reproducible across pools of differing size, sole possessor at the best end, defined for a pool of size one. The arithmetic that realizes it is the plan-gate choice.

| Alternative  | Approach                                                                                                                                                                                                                                                  | Pros                                                                                                                                                                                                                                                                        | Cons                                                                                                                                                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A (selected) | Best-end-zero linear normalization over the dense-rank span: `position = maxDenseRank > 1 ? (denseRank − 1) / (maxDenseRank − 1) : 0`, where `maxDenseRank` is the largest dense rank assigned within the possessing pool; average ascending, lowest best | Best end is exactly 0, worst exactly 1, sole possessor 0 (no division by zero) — every SPEC-004 property satisfied directly; span uses the dense-rank maximum so ties compress the scale consistently with dense ranking; pure integer-derived rational, fully reproducible | Position is relative to the _observed_ dense-rank span, so a tie at the worst end shrinks the effective span — an intended consequence of dense ranking, documented                                                                             |
| B            | Count-based denominator: `(denseRank − 1) / (poolCount − 1)`, dividing by the number of possessing targets rather than the max dense rank                                                                                                                 | Familiar "rank out of N" intuition                                                                                                                                                                                                                                          | Under dense ranking, `poolCount` can exceed `maxDenseRank` when ties exist, so the worst-ranked target would not reach position 1 — breaks the "worst end" anchor and makes the scale depend on tie multiplicity rather than distinct standings |
| C            | Best-end-one orientation: `1 − (denseRank − 1) / (maxDenseRank − 1)`, best = 1, average descending                                                                                                                                                        | Higher number reads as "more popular"                                                                                                                                                                                                                                       | Inverts SPEC-004's fixed "ascending, best average first" ordering direction; would force a re-statement of the ordering clause and invite an off-by-one between the score sense and the sort sense                                              |

Selection rationale: Alternative A is the unique realization that makes every property SPEC-004 fixes hold by construction — best end 0, worst end 1, sole possessor 0, no undefined value for pool size one — while keeping the ordering direction exactly "ascending, best average first" as the spec fixes it. Dividing by the maximum dense rank (not the possessing count) is required for the worst-end anchor to hold under dense ranking with ties, which is the precise failure mode of Alternative B.

## Architectural decisions and rationale

### 1. Normalization and scoring — pure, deterministic, recompute-from-raw

Motivated by INIT-006 Objective 1 (one objective, reproducible ordering) and SPEC-004 Aggregation model and Deterministic total order. A single pure scoring component takes the recorded raw signals and produces per-signal dense ranks, normalized positions, per-target average scores, and the resolved total order, with no external query.

- **Per-signal dense ranking.** For each signal, the targets that possess it are ranked with rank 1 most popular; equal raw values share a rank and the next distinct value takes the immediately following rank with no gap (SPEC-004 Aggregation model §3). This is computed from the recorded raw values alone, independent of input order.
- **Normalization (the deferred arithmetic, now fixed — Alternatives A).** Each dense rank maps to `position = maxDenseRank > 1 ? (denseRank − 1) / (maxDenseRank − 1) : 0`, where `maxDenseRank` is the largest dense rank in that signal's possessing pool. Best end is 0 (most popular), worst end is 1, a sole possessor is 0; the pool basis is the possessing set only, so an absent target perturbs neither ranks nor positions of participants (SPEC-004 Aggregation model §4).
- **Scoring.** Each target's score is the arithmetic mean of its normalized positions over the signals it possesses (SPEC-004 §5). A target with no possessed signal cannot occur — every target counts two or three signals (Data-source feasibility status) — but the component still defines such a degenerate target's position deterministically by the tie-break alone, never by error.
- **Total order.** Ascending by average position (lowest best); exact ties broken by canonical target name, case-insensitive ASCII lexicographic ascending, over the fixed canonical set (Aider, Claude Code, Cline, Continue, GitHub Copilot Chat, OpenAI Codex, OpenCode, RooCode) (SPEC-004 Deterministic total order §2–§3).

Trade-off accepted: rank-based aggregation discards magnitude and distance, so a target best within a thinly-possessed signal attains the top position on it (SPEC-004 §6); the artifact ships the documented acknowledgment of this pool-size property (AC4). This component is pure and side-effect-free so it is exercised by unit tests and reused identically by the build-time tool and by any recomputation from history.

### 2. Versioned data artifact — one compiled-in typed module (Alternatives A)

Motivated by INIT-006 Objective 2 (one versioned source) and SPEC-004 Single source of truth and Recorded provenance. Exactly one generated TypeScript module in the archiving feature's source tree holds, per target: the raw signals with each signal's source and the period it belongs to; the computed score; the resolved order; the refresh timestamp/period (the "as of" value); and the pool-size-property acknowledgment text. The module additionally exports, as named constants parallel to the pool-size acknowledgment text, the not-an-endorsement disclaimer text and a method-pointer (a URL or in-repository document reference to the documented aggregation method), so that the artifact — itself a public surface of the order (INIT-006 reputational posture: the disclaimer and method pointer must be co-located with _every_ public surface, the published data artifact included) — carries the disclaimer wherever it is read, not only on the README. It is frozen and typed, imported directly by the runtime (zero new dependency, no runtime read), and bundled by esbuild like any source module. A generated-file provenance header marks it do-not-hand-edit and points to the refresh procedure (SPEC-004 Build-time refresh §6). Because it is a committed source diff, each monthly refresh that changes a signal or score is a reviewable version-control delta naming every change (AC16), and a bad refresh is recoverable by reverting to the prior known-good module (AC17).

### 3. Build-time fetch tooling — `scripts/` Node utility, scheduled CI, PR-gated, validity-contracted (Alternatives A)

Motivated by INIT-006 Objective 3 (self-refreshing under minimal ownership) and SPEC-004 Build-time refresh, Error handling, Constraints 1/7/8. A Node script under the existing build-script directory, invoked by a dedicated package script and a new scheduled monthly CI workflow, queries the verified sources using only the runtime platform's built-in HTTP capability and Node built-ins (no added dependency), applies the per-source validity contract, computes scores via the decision-1 component, writes the artifact module, regenerates every README generated region (decision 5), and opens a pull request — it never pushes to the published branch (SPEC-004 Build-time refresh §4, AC14). The tool queries only the counted surfaces recorded in the feasibility table; the GitHub Copilot Chat CLI package (`@github/copilot`) is not among them, consistent with that target's product-identity exclusion.

- **Per-source validity contract (SPEC-004 Constraint 7, the deferred definition).** A response is accepted as authoritative only when: the expected count field is present at the verified path; its value is an integer at least zero; and the response carries the period the refresh targets (or the period is unambiguously the current monthly window). Any response failing any clause — a non-2xx status, a 2xx carrying malformed or partial data, a schema-drifted path, a throttled or stale zero, or a value whose period is staler than the monthly freshness bound — is recorded as an absent signal for that target and family for that period, never as authoritative, and never aborts the run (SPEC-004 Error handling §1, AC15). Two source-shape-specific clauses strengthen the throttled/stale-zero defense:
  - **npm (period present in body).** The response's `start`/`end` window fields must name the expected monthly window; a body whose window is stale (an older cached period) or whose window does not cover the targeted month is treated as absent rather than as an authoritative zero, so a stale-cached zero cannot be recorded as a real zero.
  - **PyPI (no period in body).** The PyPI-stats body carries no period field, so a returned zero cannot be period-validated. The contract applies a zero-floor for packages with known download history: a verified-existing package (one whose CLI identifier is confirmed in the feasibility table and which has demonstrated nonzero history) that returns 0 is treated as an absent signal for that period, not an authoritative zero — because an established package reporting zero monthly downloads is far more likely a throttled or stale response than a true value. A first-seen package with no recorded history is exempt from the floor (a genuine zero is possible for a brand-new package); a package is first-seen when it is absent from the prior committed artifact's recorded signals, and once it has appeared with a nonzero count the floor applies thereafter — a determination derivable statelessly from the artifact's own history. Every CLI target in this plan is an established package, so the floor applies to all of them.
- **Credential handling (SPEC-004 Constraint 8, the deferred specification).** Two distinct credentials are in play and must not be conflated. The first is the optional, read-only, minimal-scope GitHub token used only to _read_ public-repository star counts (public-repository read; no write, no private scope), supplied as a CI secret, never embedded in the extension or the committed artifact; it is optional — a token-absent run still completes within the anonymous ceiling — and rotation follows the repository's standard CI-secret rotation. The second is the `GITHUB_TOKEN` write-scope credential the scheduled workflow uses to _open_ the refresh pull request (contents and pull-request write scope on the repository); this is the action's own job credential, not a popularity-data source credential, and it is the only write-scoped credential the workflow holds. npm, PyPI, Marketplace, and Open VSX are queried anonymously.
- **Sanity bound (SPEC-004 Error handling §4, adopted; concretely defined here).** The sanity-bound metric is the count of pairwise position inversions between the new resolved eight-target order and the previously committed order — that is, the number of target pairs whose relative order flipped between the two orders (Kendall-tau distance over the eight targets). The default threshold is **more than 2 inverted pairs flags the refresh pull request for heightened editorial review**; a refresh within the bound (zero, one, or two inverted pairs) is treated as routine. The threshold lives as a single named constant in the build-time tool source — a build-time editorial-review trigger, never a runtime value and never read by the running extension. When a refresh exceeds the bound the tool still opens the pull request (it never suppresses a change) but flags it for the maintainer's heightened attention rather than presenting it as routine, so an anomalous data glitch meets editorial review before merge (INIT-006 dual governance-and-editorial gate). The monthly-refresh pull-request template (decision 5) surfaces this flag status as the first editorial-checklist item. On the first refresh with no prior committed order to compare against, the bound is skipped and the flag is not set; the pull request still opens.
- **Repeatability (SPEC-004 Build-time refresh §2, AC8).** Given the same external responses the tool produces the same artifact byte-for-byte; a refresh that finds no change leaves the resolved order unchanged and records the refresh period.

### 4. Runtime ordering integration — sort by stable provider `name` (Alternatives A)

Motivated by INIT-006 Objective 1–2 and SPEC-004 Single source of truth §2/§4 and Constraint 9. The default-provider composition sorts the instantiated providers by their immutable `name` identity against the resolved order in the artifact; a provider whose `name` is absent from the order sorts after all ranked providers, then alphabetically — a defensive default that never errors and never blocks (SPEC-004 Staleness behavior, Error handling §3). This is the only runtime consumption of the order; every user-facing enumeration, archive-related output ordering, and log naming reads through this single sorted list (SPEC-004 Single source of truth §2). The order is presentational only: it changes the sequence in which providers are enumerated, never which sessions any provider discovers, matches, parses, or archives.

### 5. README generation and consistency — per-fragment generated regions from the same source (Alternatives A)

Motivated by INIT-006 Objective 4 (documentation matches the runtime) and SPEC-004 Single source of truth §3, AC9. SPEC-004 AC9 requires that _every_ README assistant enumeration and _every_ count claim name all eight targets in the resolved popularity order. Those enumerations are inherently in separate prose locations: the "Supported assistants" table, the intro prose enumeration of the supported assistants, the "Why Tangyr Workbench" feature-bullet enumeration, and the "X assistants" count claim each sit in their own part of the README and serve their own readers. The build-time tool regenerates each of these order-bearing fragments inside its own delimited generated region, rewritten in place from the single resolved order: the table rows (one per target, all eight, in the resolved popularity order), the intro prose enumeration (all eight in order), the feature-bullet enumeration (all eight in order), and the count claim (reported as eight). The not-an-endorsement disclaimer, the pointer to the documented method, and the "as of `<last refresh>`" marker (INIT-006 reputational posture and "as of" requirement) form a co-located block in the table region. The currently-documented five expand to all eight, adding Aider, RooCode, and Continue in the table and in every prose enumeration (SPEC-004 Single source of truth §3). Each fragment is wrapped in its own delimiter pair so the generator rewrites it in place without disturbing the surrounding hand-written prose; the README is not restructured to make the fragments contiguous (Alternatives A — the per-fragment approach the Human selected over consolidation). A consistency test parses every generated region — the table, each prose enumeration, and the count — and asserts that each one names all eight targets in the resolved popularity order, that they agree with one another, and that they agree with the runtime sorted order and the artifact's resolved order, failing the build on any drift in any region (AC1, AC9).

The monthly-refresh pull request is opened from a dedicated pull-request template carrying a three-item editorial checklist, so the dual governance-and-editorial merge gate (INIT-006) is auditable rather than a rubber stamp: (1) the sanity-bound flag status (whether the refresh exceeded the inverted-pair bound of decision 3); (2) the top-N position delta (which targets moved in the resolved order and by how much); and (3) any zero-signal or single-signal targets in this refresh (a target that dropped to one counted signal, or whose signals fell to absent, since the prior refresh). The maintainer confirms each item before merging, making the editorial judgment a recorded checklist rather than an implicit one.

### 6. Provider-registry order-sensitivity audit and swap-invariance (SPEC-004 Constraint 9, AC18)

Motivated by SPEC-004 Constraint 5 (archiving correctness unchanged) and Constraint 9. The plan audits the registry for any path where provider order influences which sessions are discovered, matched, or archived — provider iteration during a cycle, workspace-matching, deduplication, and replacement bookkeeping keyed by `archiveName`. The audit has two parts:

- **Static search for order-dependence.** A static search of the registry and matching path for any index-referencing or position-referencing branch — any logic that reads a provider's position in the list, the list length, or an array index to decide discovery, matching, deduplication, or archiving behavior. The expected finding is none: matching is keyed by `archiveName` and per-provider workspace filtering, not by list position.
- **Swap-invariance regression test.** The audit's finding (no order-sensitive matching/archiving path; ordering affects enumeration sequence only) is locked by a swap-invariance regression test that runs an archive cycle under multiple provider orderings and asserts the set of discovered, matched, and archived sessions is identical for a workspace (AC18). The permutations exercised are: (a) the natural order versus the fully reversed order as the baseline; and (b) a targeted adjacent-pair swap of the two providers with the most-overlapping `archiveName` keyspaces — Cline (`cline-<taskId>`) and RooCode (`roo-code-<taskId>`), both global-scoped, both keyed by a task identifier, and the closest sibling pair (RooCode is a Cline derivative) — so the test stresses the precise pair most likely to expose an order-sensitive deduplication or replacement collision if one existed.

Together the static search and the multi-permutation swap-invariance test are the structural guarantee that the presentation-order change cannot leak into provider behavior.

### 7. Maintenance ownership, acceptable-staleness window, and active staleness surfacing (SPEC-004 Build-time refresh §5, AC21 — the deferred resolution)

The designated maintenance owner of the monthly refresh is the project maintainer (the same human who holds the merge authorization and the dual governance-and-editorial gate, per INIT-006). The acceptable-staleness window is one calendar month beyond the monthly cadence: the recorded data may lag up to one cadence period before the lag warrants the owner's attention. One cadence period is the justified window because the refresh runs monthly and a single missed cycle is recoverable on the next scheduled run without any reader-visible degradation (the order still resolves deterministically from stale data, SPEC-004 Staleness behavior §1); a window shorter than one cadence would flag normal between-refresh lag as overdue, while a longer one would let two or more cycles silently lapse before surfacing — one cadence period is the smallest window that distinguishes routine lag from genuine abandonment.

Staleness is surfaced two ways. Passively, the "as of" marker on every public surface makes the recorded period self-evident to a reader (INIT-006), and the absence or delay of the monthly refresh pull request is the standing signal that a refresh is overdue (SPEC-004 Staleness behavior §2). Actively, a scheduled CI staleness-probe job inspects the committed artifact's recorded period and, when that period exceeds the staleness window plus a grace period (one cadence period plus a short grace, so a refresh PR that is merely a few days late does not trip it), opens a GitHub issue announcing that the ranking is overdue — so abandonment is actively raised rather than depending on someone noticing a missing PR. Both the owner and the window are documented in the repository surface alongside the refresh procedure (SPEC-004 Build-time refresh §6, AC20 — discoverability portion).

## Increments

Single workstream is appropriate: the scoring component, artifact, tooling, runtime sort, and README generation share the single-source contract tightly, and the increments are strictly sequential (each consumes the previous increment's output), so splitting across concurrent agents would fracture that contract. Internal increment order below; each increment is self-contained and introduces no forward reference.

### Increment 1 — Pure scoring and ordering component

**Objective**: Deliver the deterministic dense-ranking, normalization, averaging, and total-ordering logic as a pure component that turns recorded raw signals into a resolved order.

**Dependencies**: none.

**Requirements covered**: SPEC-004 Aggregation model §1–§8; Deterministic total order §1–§4; Missing-surface tolerance §1–§2; AC2, AC3, AC4 (acknowledgment text constant), AC5.

**Interventions**:

- Implement the per-signal dense ranking, the best-end-zero normalization fixed in Decision 1, the average-over-possessed-signals scoring, and the ascending order with the case-insensitive ASCII canonical-name tie-break, as a pure component with no external access.
- Define the typed shape of a target's recorded signals and of the resolved order, and the pool-size-property acknowledgment text constant.

**Verifiable output**: Unit tests prove dense-ranking with ties, pool-comparable normalization across pools of differing size, the sole-possessor best-end value, averaging over possessed signals only, ascending order, the alphabetical tie-break, and input-order independence (identical output across shuffled inputs). The enumerated cases include: a pool of size one (sole possessor maps to best-end 0); a partially-tied pool (a shared rank followed by the next distinct value with no gap); a fully-reversed input order producing the same resolved order; an exact average-score tie resolved by the alphabetical tie-break; and the all-tied pool, in which every target shares one raw value on a signal so all receive dense rank 1 and all map to the best-end position 0 (`maxDenseRank` equals 1, exercising the `maxDenseRank > 1` guard's false branch).

### Increment 2 — Versioned data artifact shape and runtime ordering integration

**Objective**: Introduce the single compiled-in artifact module shape and make the provider registry consume a resolved order of that shape, so runtime enumeration follows the single source.

**Dependencies**: Increment 1 (the resolved-order shape and scoring component).

**Requirements covered**: SPEC-004 Single source of truth §1–§2/§4; Recorded provenance §1; Staleness behavior §1–§2; Constraints 1/2/3; AC1, AC7, AC11; partial AC10 (recorded period present, runtime resolves deterministically).

**Interventions**:

- Define the generated artifact module's typed shape (typed, frozen, carrying a do-not-hand-edit provenance header) holding per-target raw signals, source, period, score, resolved order, refresh timestamp/period, the pool-size acknowledgment text, the not-an-endorsement disclaimer text constant, and the method-pointer constant. No real generated artifact instance is produced in this increment; the runtime contract is exercised against a local fixture instance of this shape. The first real artifact instance is the build-time tool's first deliverable in Increment 3.
- Sort the composed default-provider list by stable provider `name` against the resolved order's `name`-keyed sequence, with the defensive after-all-ranked-then-alphabetical default for any unranked `name`; route all runtime enumeration through this single sorted list.

**Verifiable output**: Unit tests against the local fixture confirm the runtime order equals the fixture's resolved order, that an unranked provider name sorts last deterministically, and that the runtime path performs no network call and no filesystem read of the artifact (it is a module import). The existing bundle-asset external check — the integration test asserting that the only non-Node-builtin external require in the built bundle is `vscode` — remains green and is the enforcing step that the artifact module introduces no new external dependency.

## Risks and mitigations

- Risk: A data source changes its response schema between refreshes (schema drift), silently corrupting a signal.
  Mitigation: The per-source validity contract (Decision 3) treats any unexpected shape as an absent signal rather than authoritative (SPEC-004 Constraint 7, AC15); the affected target keeps a defined score from its remaining signals.
- Risk: GitHub anonymous rate limits throttle the star queries on a shared CI runner IP, zeroing stars.
  Mitigation: The optional read-only token raises the ceiling; a throttled response is recorded absent for that period, not zero (Decision 3); the eight queries fit even the anonymous ceiling, so this is robustness, not correctness.
- Risk: A registry that returns a stale or throttled zero is recorded as an authoritative zero, silently demoting a target.
  Mitigation: The throttled/stale-zero clauses of the validity contract (Decision 3) — the npm window-field check and the PyPI known-history zero-floor — treat such a zero as an absent signal rather than authoritative, each covered by a per-source fixture test (Increment 3).
- Risk: A README hand-edit outside a generated region, or inside one between refreshes, drifts from the runtime order.
  Mitigation: The consistency test (Decision 5) parses every generated region and gates the build on README/runtime/artifact agreement across all of them (AC9); each fragment's own delimiter pair narrows the hand-editable surface around it.
- Risk: A future reordering accidentally couples to provider matching, changing archive output (the precise hazard SPEC-004 Constraint 9 guards).
  Mitigation: The order-sensitivity audit (static search plus the multi-permutation swap-invariance test, including the Cline/RooCode adjacent swap) proves discovery/matching/archiving is invariant under reordering (Decision 6, AC13, AC18).
- Risk: An anomalous refresh (data glitch) proposes a wildly reordered ranking.
  Mitigation: The month-over-month sanity bound (more than two inverted pairs) flags the pull request for the maintainer's editorial review, surfaced as the first item of the editorial PR checklist before merge (Decision 3/5, INIT-006 dual gate, AC14).
- Risk: The maintenance owner lapses and the ranking silently goes stale, while readers still see an order that implies currency.
  Mitigation: The "as of" marker makes staleness self-evident (INIT-006), and the active staleness-probe job opens a GitHub issue once the recorded period exceeds the window plus grace (Decision 7), so abandonment is raised rather than only passively visible.
- Risk: The scheduled refresh workflow fails silently, indistinguishable from a deliberate no-change month.
  Mitigation: The on-failure notification (Decision 5/Increment 4) opens or annotates an issue on workflow failure, so a failure-to-open-a-PR is distinguishable from a no-change month.
- Risk: The artifact module is hand-edited, diverging the recorded signals from the resolved order.
  Mitigation: The do-not-hand-edit provenance header plus the recomputable-from-raw property (Decision 1/2) make any hand-edit detectable by recomputation; the consistency test catches an order that does not match the recorded signals.
